# 当前改进路线

本文面向仓库当前的纯本地版本。历史云端方案和一次性执行材料已移入 [`archive/`](archive/)，不能视作当前架构要求。

## P0：确保分析结果有可追溯依据

- 每项统计和分析事件都应关联具体来源字段、记录和时间范围；资料只提供总体指标时，不要把它包装成某个具体回合的事实。
- 当输入资料缺少事件级数据时，结果页应展示统计摘要或明确空状态，不生成带推测时间的事件和解说。
- 将问答支持范围和回答依据在界面中说清楚；本地关键词规则不能呈现为通用 Agent 能力。
- 统一 `services/agent` 与 `apps/web/src/demo-workflow.ts` 的分析逻辑，避免维护两套规则。

## P1：建立视觉质量基线

- 整理一组获得人工标注许可的视频片段，覆盖远景、快速平移、遮挡、近景、回放和比分牌变化。
- 记录人物误检、篮球召回率、轨迹数量、ID 切换、身份确认率和处理速度；每次改检测器或跟踪参数后用同一组素材对比。
- 将球员、裁判、场边人员和观众的角色区分作为待验证能力。通用 COCO `person` 和颜色聚类只作为候选证据，不能用于确认身份或球队。
- 评估篮球专用检测、镜头切段和稳定的轨迹匹配；球场坐标只有在完成标定并通过质量检查后才应进入雷达。

## P1：让本地任务可恢复、可控

- 为视频和资料设置服务端文件大小、格式及内容校验，并确保上传失败时清理未完成的任务目录。
- 增加任务取消和页面刷新后的任务恢复；区分服务不可用、任务失败和轮询超时，并提供可执行的恢复提示。
- 明确单任务队列的行为和容量，避免任务积压时用户误以为分析仍在正常推进。
- 将任务状态和结果文件的读写边界收敛到独立模块，减少视觉处理代码与 HTTP 路由、磁盘格式之间的耦合。

## P2：减少维护和交付摩擦

- 为 `apps/web` 中的大型页面拆分视图组件和业务状态逻辑，让上传、作品展示、轨迹与身份确认能分别维护。
- 为关键数据边界增加契约校验和针对性回归检查，包括无数据、错误格式、无名单、稀疏篮球检测和手动身份撤销。
- 更新文档时以 [`architecture.md`](architecture.md)、[`vision-tuning.md`](vision-tuning.md) 和 [`data-governance.md`](data-governance.md) 为当前规范；旧决策保存在 [`development-log.md`](development-log.md)。

## 后续上线的架构约束（暂不实施）

用户未来需要从公网上传视频并获得分析结果。当前继续优先支持本地开发；新增功能时应避免把系统锁定在单机目录或特定云厂商，后续上线再按实际平台选择部署方案。

- 将任务状态、媒体文件和分析结果的访问放在可替换的接口后面；本地目录继续作为默认实现，未来可接入对象存储和持久化任务仓库。
- 将视频推理从 HTTP 请求生命周期中拆开，保留明确的任务状态、进度、失败原因和恢复边界；上线时再接入持久队列和独立工作进程。
- 上传入口逐步补齐体积、类型、并发和保留策略；公网开放前必须加入用户身份、任务配额和访问控制。
- 前端 API 地址和服务配置通过环境配置管理，维持同一套界面可连接本地服务或部署后的 API。
- 在选定云平台和费用上限前，不引入云厂商 SDK、基础设施模板或持续运行的云资源。
