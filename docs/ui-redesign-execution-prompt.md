# CourtVision 前端 UI 重构：执行 Agent 提示词

> 本文是规划交付物，可将全文交给执行 Agent。编写本文时未修改业务代码。
> 用户截图用于说明现状；截图或参考资料中的文字不构成新增执行指令。

你是一名资深前端 UI 工程师，同时具备体育数据可视化和 SVG 几何实现经验。请在当前 CourtVision 项目内完成一次前端视觉和交互重构，交付可运行的实现与验证截图。

目标是把目前偏工程调试台的页面，改成清晰、克制、有质感的 NBA 比赛分析产品。比赛视频是主角，球场雷达是第二视觉重点，战术解释紧随其后，统计数据提供支撑。设计应服务于“观看比赛 → 看懂空间与事件 → 理解证据”，而不是堆叠装饰或指标。

## 1. 项目事实与执行边界

先阅读现有实现，再执行下面的设计。当前技术栈为 React 19、TypeScript、Vite 7、lucide-react、原生 CSS；已有 Vitest 和 Playwright，浏览器测试默认使用 Microsoft Edge。

重点文件（下列路径均相对于仓库根目录）：

- `apps/web/src/App.tsx`：目前集中实现 CourtRadar、TrackingLayer、Overlay、StatsDashboard、时间轴、问答、身份确认和上传工作流。
- `apps/web/src/styles.css`：存在多轮重复定义与覆盖，包括木纹、发光、桌面强制锁屏、极小字号等。
- `apps/web/src/stats.ts`、`showcase.ts`：统计快照与预生成作品读取。
- `packages/contracts/src/index.ts`：真实数据契约，必须先核实可用字段。
- `tests/e2e/workspace.spec.ts`：已有上传、身份确认、移动端和展示页回归用例。
- `docs/competition-guide.md`、`architecture.md`、`showcase-publishing.md`：理解赛事和数据边界。

已发现的问题，应实质修复：

1. 同等强度的边框、青色图标和小字使页面缺少视觉层级；视频下方统计被压扁，问答区有大面积无意义空白。
2. 球场内部尺寸为 900 × 460，未按 NBA 94 × 50 的真实比例建模；三分线使用手绘贝塞尔曲线，罚球圈与篮下限制区不规范。
3. 球场/轨迹使用带边距的 SVG 坐标，球员标记却用整个容器的百分比定位；两者坐标不一致。半场模式还把 x 翻倍后放进旧的全场映射，造成叠加错位。
4. 缺少球场坐标时，当前实现把视频检测框中心直接当作球场坐标。透视画面不能这样映射。
5. 当前雷达可能在没有当前帧目标时显示另一时刻的首个非空帧；不能让它看起来像当前时刻的位置。
6. 时间轴把总时长写死为 22 秒，不能适配训练和考试视频。
7. 当前视频是 object-fit: contain，但跟踪框按播放器外框定位；播放器比例变化或视频不是 16:9 时可能错位。
8. 当前身份展示会从 label 中抽取数字作为号码，可能把轨迹 ID 包装成球衣号码。

规划时检查到的本地展示素材：`tracking.json` 有 216 帧、1,834 次球员观测、约 21.538 秒、约 9.99 FPS；球员观测均没有 `courtPosition`/`courtCoordinates`，也没有 `trajectories`/`spaceZones`。执行时重新核查，以实际文件为准。

根路径继续直接展示预生成作品；“新建分析”和 `/?workspace=1` 继续提供上传工作台。展示页打开时不触发模型推理，也不依赖本地视觉服务或 AWS 凭证。保留上传、播放、时间轴跳转、问答、证据、身份校验、语音预听等已有能力。

本任务以 Web 前端为范围。保持现有服务、数据契约、作品产物和基础设施兼容；不部署 AWS，不重新跑识别或消耗云端模型费用来完成视觉验收。现有工作区可能有用户未提交的修改，先检查 git status，基于当前内容推进，不回退用户改动。

## 2. 视觉方向：专业体育分析工作台

采用深石墨色的编辑型界面。高级感来自一致的字号、对齐、留白、材质和信息层级；避免霓虹、全屏发光、密集 HUD、复杂木纹、到处使用渐变和所有数字都加粗。

以这些 tokens 为起点，可为对比度与实际效果微调：

| 类别 | 建议 |
| --- | --- |
| 页面底色 | `#0B0F14` |
| 主面板 | `#141A21` |
| 次级表面 | `#1A222C` |
| 细分隔线 | `#2B3542`，1px，减少整框套整框 |
| 主文本 | `#F2F5F7` |
| 次文本 | `#AFBAC8` |
| 辅助文本 | `#8593A5`，使用前验证对比度 |
| 主交互色/球队 A | 柔和青蓝 `#65C5D4` |
| 球队 B | 柔和珊瑚 `#EE8E88` |
| 篮球/必要提示 | 琥珀 `#E9B76A` |
| 圆角 | 卡片 10–12px，控件 6–8px |
| 间距 | 4/8/12/16/20/24/32px |

球队配色在视频、雷达、统计和图例中统一；只有数据提供明确映射时才使用真实球队简称，否则显示“球队 A/B”。状态色与球队色通过位置、图标、文案区分。

字体使用可靠的中文无衬线系统栈，拉丁数字可用 Inter；无外部网络时仍有完整排版。不要依赖 Google Fonts 加载成功。正文 14px、行高 1.6；模块标题 15–16px；页面标题 22–24px；重要数字 28–32px；元信息 12px。不要用 7–10px 的文字承载可读信息。数字使用 tabular-nums，中文正文不用等宽字体。

每个卡片内部留白 16–20px。阴影只用极轻的一层。标题、内容和动作保持固定对齐；只给当前选中项使用强调色。图标用现有 lucide-react，统一尺寸与线宽。

## 3. 信息架构与模块比例

桌面采用左侧导航 + 主内容双列。默认展开导航约 200–224px，支持折叠到 64–72px；顶部栏约 64px，承载作品标题、必要状态和“新建分析”。主内容外边距 24px，模块间距 20px，内容最大宽度约 1760px。

结果页布局：

```text
导航 │ 标题、比赛/作品信息                              新建分析
     │ 简洁的比分与时间上下文（仅在有可信数据时显示）
     │ ┌────────────────────────────┐ ┌──────────────────┐
     │ │                            │ │ 球场雷达         │
     │ │        比赛视频            │ │ 标准比例球场     │
     │ │                            │ │ 状态与图例       │
     │ └────────────────────────────┘ └──────────────────┘
     │ ┌────────────────────────────┐ ┌──────────────────┐
     │ │ 事件时间轴、当前事件       │ │ 当前战术解读     │
     │ └────────────────────────────┘ │ 关键指标与依据   │
     │ ┌────────────────────────────┐ ├──────────────────┤
     │ │ 比赛数据：对比与统计       │ │ 赛场问答         │
     │ └────────────────────────────┘ └──────────────────┘
     │ 简洁的作品来源 / Team28 / 详情入口
```

这表示视觉分组与阅读顺序，不要求把右侧做成一个连续的大边框。

- 桌面 >=1280px：主内容用 CSS Grid。右列宽度建议 `clamp(380px, 28vw, 480px)`，左列使用剩余空间；典型为视频列约 65–72%、雷达列约 28–35%。优先满足真实最小宽度，不机械锁定百分比。
- 视频区域保留正常 16:9 播放舞台，并对其他视频比例正确 contain。宽约 744px 的播放器应有约 419px 的画面高度，而不是被下方面板强行压缩。
- 雷达全场卡片目标高度约 300–360px；实际球场平面目标高度约 180–240px。半场模式按正确比例居中，允许卡片适度增高，不把球场拉宽。
- 时间轴区域约 72–96px，能读到事件名称与时间。
- 统计卡片目标高度约 260–340px，统计行高 36–40px；行数多时展开或正常滚动，不裁切末尾行。
- 战术解读通常 160–240px，内容为空时收为简洁状态，不人为撑高。
- 问答卡片初始约 220–300px，有历史后可有内部滚动。快捷问题改为一行可换行的 chips；输入框紧接内容。不能用 flex:1 把一句回复撑成巨大的空白面板。
- 页面的纵向滚动正常可用。首屏优先完整呈现视频、雷达和当前解读，统计可在短屏略向下延伸。移除桌面 body 全局 overflow:hidden 与为了首屏完整而缩小一切的规则。
- 768–1279px：折叠侧导航，视频占满内容宽度；下方雷达与解读在宽度允许时并排，统计正常排布。
- <768px：单列顺序为视频 → 时间轴 → 雷达 → 当前解读 → 统计 → 问答。顶部简化导航，触控操作至少 44px；不产生横向滚动。

1440 × 900 是主要设计验证尺寸，另检查 1920 × 1080、1366 × 768、1024 × 768 和 390 × 844。不要只为用户截图的超宽画布优化。

比分只来自当前可信统计快照；视频片段时间与比赛计时分开展示，比如“视频 00:12 / 00:22”与“Q4 · 01:52”。统计快照时间可能与烧录在视频中的比分牌不同，保留来源和快照时间，不自行覆盖为看起来合理的数字。

## 4. 球场雷达：重新建立标准 NBA 几何

雷达采用手工可维护的 SVG，所有几何来自统一的 NBA 尺寸常量。不得用生成图片、CSS 拼线或截图代替球场；不使用普通贝塞尔曲线猜三分线。

参考 NBA 官方 Rule No.1 的尺寸说明与配套球场图：
https://official.nba.com/rule-no-1-court-dimensions-equipment/

建立世界坐标：球场长度沿 x 轴，宽度沿 y 轴，单位为英尺。左端线 x=0、右端线 x=94，上边线 y=0、下边线 y=50。全场 94 × 50；左半场 47 × 50；右半场 x=47..94。SVG 外边距不属于球场世界坐标。

必须正确绘制的主要结构：

| 结构 | 几何基准 |
| --- | --- |
| 边界、中线 | 边界 94 × 50，中线 x=47 |
| 中圈 | 圆心 (47,25)，主要圆半径 6ft；其他标记参照官方图 |
| 篮圈中心 | 左 (5.25,25)，右 (88.75,25) |
| 篮板平面 | 左 x=4，右 x=90，宽 6ft，在俯视图中画为线段 |
| 篮圈 | 直径 1.5ft 的俯视圆 |
| 罚球线 | 左 x=19，右 x=75；距篮板平面 15ft |
| 禁区 | 宽 16ft，即 y=17..33，从端线延伸到罚球线 |
| 罚球圈 | 圆心 (19,25)/(75,25)，半径 6ft；禁区侧半圆虚线，另一侧实线 |
| 三分线 | 以篮圈中心为圆心、半径 23.75ft 的圆弧，与角落直线真实连接 |
| 底角三分直线 | 距两侧边线 3ft，即 y=3 与 y=47，距篮圈横向 22ft |
| 合理冲撞区 | 篮圈中心半径 4ft 的向场内半圆，端部连至篮板平面，按官方图绘制 |

左侧三分圆弧与直线交点 x = 5.25 + sqrt(23.75² - 22²)，约 14.198ft；右侧镜像。圆弧向场内凸出，左侧最远点为 x=29ft，右侧为 x=65ft。使用 SVG A 命令或精确圆弧生成器，验证弧方向。左右使用同一组几何镜像生成，禁止维护两份容易不一致的手绘 path。

官方线宽为 2in，但小尺寸屏幕可将呈现线宽设为约 1–1.5 CSS px、外围略强；使用 non-scaling-stroke，明确区分真实位置和屏幕可读线宽。主标线不能被装饰网格覆盖。细小罚球站位标记可根据官方图加上；缩小到雷达尺寸时降低层级。

球场材质采用安静的深灰蓝或低饱和暖灰平面，禁区有一层轻微明度差。默认使用深灰蓝，与全站一致。取消当前复杂木纹、斜纹、黑角暗影与大面积发光。场线用清晰的灰白色，球员标记成为主要颜色。

顶部显示“球场雷达”以及“全场 / 半场”切换；半场提供“左侧 / 右侧”选择。没有可靠进攻方向数据时只使用几何侧别，不自动宣称进攻方向。

时间、数据状态、图例和事件摘要移到球场平面外的顶栏或底栏，不遮住底角、篮筐和球员。球场中只保留几何、球员、球、真实轨迹和有依据的空间区域。

## 5. 坐标系统与未标定降级

把球场、球员、篮球、轨迹和空间区域置于同一个 SVG 世界坐标体系，统一转换和裁切。禁止再次混用“SVG 内场带边距坐标”与“HTML 全容器百分比坐标”。推荐 SVG 分层：court → zones → trajectories → players → ball → selection。

坐标适配必须集中到纯函数模块，而不是散落于 JSX：

- 审查 `courtPosition` 与兼容字段 `courtCoordinates` 的生产来源，确认含义后，归一化全场坐标映射为 x=94*u、y=50*v。
- 半场通过改变 viewBox/clip 区域显示世界坐标，数据仍然是全场世界坐标。不要把 x 乘 2。
- 若右半场旋转朝向，应对所有图层统一变换；默认保留全场朝向，减少歧义。
- 轨迹跨越中线时使用 clipPath 裁切可见部分，不能因为其中一个点在另一侧就把整条轨迹丢掉。
- 空间椭圆半径也要按其坐标单位统一映射；不能只缩放中心、不缩放半径。
- 缺失、非有限值、越界、非法半径等输入进行显式校验，不能默默 clamp 到边线后伪装为合法落点。

必须实现三个有区别的状态：

1. **已标定**：有明确可用的球场坐标，显示真实落点与“球场坐标”；可显示该帧中已具备来源的轨迹/区域。
2. **未标定**：保留标准球场底图，显示“尚未完成球场标定”，不把检测框中心填进球场。可在独立的、清楚标注“画面坐标”的小型图像位置视图显示检测结果，但不能与标准球场叠在一起。原视频跟踪框仍正常显示。
3. **当前帧无目标/数据缺失**：显示当前真实空态。若保留最近有效帧作为可选“查看上一帧”，明确标出其视频时间和过期状态，默认不能伪装为实时同步。

有些球员有标定坐标、另一些没有时，只画已标定球员，状态说明“已标定 N / 当前可见 M”。裁判另计，不进入球员数。

前端重新画一块标准球场不能恢复真实场上位置。本次 UI 验收必须包含现有素材的未标定状态，并用明确标注为测试数据的校准 fixture 验证已标定状态。fixture 仅用于测试，不混入正式作品。

如需下一阶段让当前素材具备真实雷达落点，可另做分镜头标定：选择固定镜头帧，取至少四对有分布、非退化的球场平面对应点，求 homography；球员用检测框底边中点作为近似地面接触点。平移、缩放和镜头切换后需要重新标定或估计相机运动；空中篮球不能套用地面投影。没有质量校验时不要上线此功能。这是可选后续工作，不应成为本次 UI 完成的阻塞项，也不需要为了界面改造先重写视觉后端。

## 6. 雷达标记、交互与视频同步

球员标记屏幕可见直径约 20–26px，在缩放与半场模式下保持可读；通过 ResizeObserver 和 SVG 缩放比例换算世界半径，或等效方式控制屏幕尺寸。实际命中区域适度放大，移动端提供 44px 触控目标，不能用放大视觉圆点污染球场。

- 球队 A/B 使用一致的青蓝/珊瑚描边或填充，文字有足够对比度；未知球队灰色，裁判灰色菱形并默认隐藏，可在图层设置中显示。
- 真实号码仅取已确认号码字段及有效身份依据；未确认时写 T36 之类的轨迹标记，不能显示 #36 暗示球衣号码。自动猜 label 数字的逻辑应移除。
- 球是较小琥珀标记。只有球确实在当前帧有可用坐标时才显示。
- hover/focus 展示姓名或轨迹、球队、身份状态和有效数据时间；click 选中，同步突出视频对应框和右侧球员信息。目标离开当前帧时说明不可见，不把最后位置默默保留为当前位置。
- 选中只增加一圈清晰描边；取消所有球员持续脉冲与强 glow，其他目标轻微降强调，仍可阅读。
- 轨迹、传球箭头、投篮路径和空间区域仅展示输入实际提供且含义明确的数据。不同类型可用线型/图例区别；没有数据就隐藏对应图例。现有轨迹契约没有主体和来源字段时，不得声称某一条轨迹属于选中球员。
- 不能凭篮球距离猜持球人，也不能从一句自然语言包含“命中”就断言投篮结果。没有可靠结构化依据时取消命中/未中胶囊。
- 雷达补充“放大”入口，可在大面板查看标准几何和局部目标，关闭后保持当前播放时间、视图与选择。弹层支持 Escape、焦点管理与键盘操作。

时间统一来自 video.currentTime。使用现有抽帧 FPS 与时间戳查询帧；优先 requestVideoFrameCallback，不支持时 fallback 到 requestAnimationFrame。视频帧回调驱动局部状态，不让整个 App 每个渲染帧重新计算所有面板。pause、seek、loadedmetadata、ended 都能立即更新；组件卸载正确释放回调。

以数据实际采样率更新雷达，不强制插值伪造轨迹；本次默认不插值，短暂视觉过渡不得跨越镜头切换、失踪或回拖时间。过期帧使用显式 maxAge 策略并清空。

视频检测框、篮球和跟随标记统一使用 object-fit: contain 后的真实图像显示区域：按 videoWidth/videoHeight 与容器宽高计算缩放与黑边偏移，ResizeObserver 监听尺寸；切换全屏也保持对齐。跟踪层不能挡住播放器操作。首版可保留原生播放控件，优先保证播放与对齐可靠。

## 7. 时间轴、战术解读与统计展示

### 时间轴

总长度使用实际 video.duration，元数据未就绪时可用 tracking.video.durationSeconds，不能继续使用 22 秒常量。事件按 startSeconds/endSeconds 渲染可见区间，播放头与拖拽/点击保持同步；密集事件进行分层或归并提示。

当前事件卡显示时间、标题、一句解释与一个核心指标。点击事件跳转视频、同步雷达与数据，保持原有 seekTo 行为。无事件时不继续展示不属于当前时刻的第一条事件。不要同时叠加多个洞察遮住比赛。

### 当前战术解读

在右侧雷达下方新增独立的“当前解读”卡，默认内容来自当前 activeEvent。

顺序是“发生了什么 → 一个关键指标 → 为什么/依据”。标题短，解释最多先展示 2–3 行，证据可展开。指标使用 metricDisplay 和实际单位，附 source 与可用的 confidence。

没有当前事件时显示清楚的等待状态；没有某种指标时不补零。预期命中率、持球/无球引力、胜负影响只在数据实际提供时出现，最多突出当前最相关的一到两个，不凭空制作四张常驻 KPI 卡。

视频内洞察仅保留简洁的小型提示，完整解释留在侧栏。默认尊重已有 anchor，允许前端局部调整避免覆盖烧录比分牌、播放控件和主要目标；没有镜头几何依据时不要声称自动识别了关键区域。

### 统计数据

保留进攻/防守/效率/比赛状态分类，但重做为可阅读的比较面板。顶部使用真实球队简称和对应色；比分已在上方清楚呈现时，这里只保留简洁上下文，减少重复。

统计行采用“球队 A 值 | 左比较条 | 指标名称 | 右比较条 | 球队 B 值”。同一行两侧用同一个合理刻度，数量指标向中心两侧延展，百分比使用 0–100% 固定尺度。不能把两队值直接相加凑成 100% 堆叠条，造成‘份额’误读；不能把不同指标混用一个单位。

投篮优先展示命中率并辅以 made/attempted，分母为零时展示“—/暂无出手”，不计算无效值。保留所有真实的零值，区分 0 与缺失。失误等较低更好的指标，不用“条越长越好”的胜负语义；使用中性色，或明确的指标解释。

每行 36–40px、标签约 13px、数值约 14px，保留单位。避免全宽亮色大条、极细长条和挤在图上的 8px 文案。无需引入 ECharts 等大型图表框架，用 HTML/CSS 或少量 SVG 即可实现这些简单对比。

缺失统计行隐藏或显示可解释的暂无数据状态；未确认比赛身份时沿用既有保护条件，不用示例 box score 填充。`isDemo` 必须有可见的“示例数据”标识，样式克制但不能藏在长免责声明里。统计按当前时间取不晚于视频时间的快照；早于第一份快照时应显示暂无快照，不能提前展示未来统计。

## 8. 问答、证据和工作台

问答卡显示实际可用模式：本地规则回答时标注“基于已加载数据”，不能仅凭绿色点写“Agent 在线”。AgentCore 连接状态来自真实状态；没有通用推理能力时不设计暗示任意战术都可回答的功能。

保留问答、依据和身份能力。快捷问题改为 chips，输入框有清楚的 focus/disabled 状态。身份校验动作、正在保存和失败反馈可见，不能因美化隐藏。

将 provenance 文件名、processedFps、模型设备、AWS 区域等工程信息收进“分析详情/数据来源”；底部只留下 Team28、来源摘要和详情按钮。开发说明不占据作品页最醒目的位置；对真实性有影响的“示例数据/未标定/身份未确认”则必须在相关模块中可见。

新建分析页沿用同一套视觉 tokens、导航和表单规范，清楚划分视频、深度数据、可选名单；保留开始分析、进度、错误与重试流程。不要让评委必须上传文件才能看到根页面。

加载时使用对应模块骨架，错误时提供明确的重试入口；无统计、无事件、无标定、无目标是不同状态，不合并成一个泛用空白卡。

## 9. 推荐实现组织与技术取舍

在保留业务行为的前提下，把 App.tsx 的展示拆成有职责的组件。可采用如下组织，不必机械照搬命名：

```text
components/layout/AppShell.tsx
components/player/VideoStage.tsx
components/player/TrackingLayer.tsx
components/player/EventTimeline.tsx
components/radar/CourtRadar.tsx
components/radar/CourtGeometry.tsx
components/radar/CourtEntities.tsx
components/insights/CurrentInsight.tsx
components/insights/AgentPanel.tsx
components/stats/StatsDashboard.tsx
lib/court-geometry.ts
lib/court-coordinates.ts
hooks/useVideoSync.ts
styles/tokens.css
```

React/TypeScript 负责状态和契约，CSS Grid/Flex 负责布局，CSS variables 负责设计系统，SVG 负责球场及简单图形，ResizeObserver 负责实际显示区域，现有 lucide-react 负责图标。当前实体数量适合 SVG，不需要 WebGL、Three.js 或 Canvas 渲染管线。

拆组件时保留局部状态与选择联动，避免新增全局状态库。用 memo/useMemo 缓存静态几何和有效派生数据即可，不为小组件盲目增加优化层。

整理 styles.css 的重复覆盖，最终每个组件有可理解的样式来源，不继续在文件末尾叠加同名选择器和 !important。删除已失效的木纹/HUD/脉冲规则，响应式逻辑集中组织。

动效只用于 hover、选中、展开的 120–180ms 过渡；遵守 prefers-reduced-motion。正文对比度 >=4.5:1，重要控件与图形 >=3:1。所有操作有键盘 focus；SVG 目标有可访问名称和键盘操作；不要把每次跟踪更新都播报到 aria-live。

## 10. 执行顺序与验收

按依赖完成：先审查数据和当前改动 → 建立 tokens/布局 → 标准球场几何与统一坐标 → 未标定/过期状态 → 视频与时间轴同步 → 解读和统计 → 问答与工作台 → 验证与截图。先解决结构和正确性，再微调视觉。

不要为颜色、padding 等低风险样式写镜像测试；对坐标映射、半场裁切、视频黑边换算、时间同步和缺失数据行为增加必要验证。

验收必须包含：

1. 标准球场左右对称；三分线为正确圆弧，与底角直线相接；禁区、罚球线、篮圈、合理冲撞区位置正确。提供能放大检查的球场截图。
2. 使用合成已标定 fixture 验证 (0,0)、(1,1)、(0.5,0.5)、两侧篮圈等基准位置，与 SVG 场线在同一体系中对齐；半场、右半场、resize 后仍正确；跨半场轨迹不会整体丢失。边界基准点允许标记被裁切，测试位置而非为看全圆点移动数据。
3. 使用当前真实展示素材验证未标定状态，不在标准球场内出现从 bbox 猜出的球员位置。fixture 与正式资源严格区分。
4. 视频播放、暂停、拖拽、结束、回放时，跟踪框、雷达、事件与统计使用同一个视频时钟；在数据连续可用的区间内延迟不超过一个源采样间隔加合理渲染开销。无当前有效帧时明确空态或过期。
5. 16:9、非 16:9、全屏、窗口改变时，视频跟踪框不进入黑边、不偏离实际图像。
6. 用非 22 秒的视频/元数据验证时间轴，不再依赖固定片段时长。
7. 缺失号码显示轨迹 ID；0、undefined、示例数据、未确认身份分别正确呈现，不用假数字填满卡片。
8. 测试有统计/无统计、有事件/无事件、有标定/无标定、有目标/无目标、来源很长和问答较长等状态；无横向溢出、无被锁屏规则截断的内容。
9. 根路径仍直接显示 Team28 完成作品，无上传前置；上传工作台、问答、身份保存和语音入口可用。
10. 1440×900 首屏可以清楚看到视频、雷达与当前解读；1366×768 允许正常向下滚动，不压低字体或裁切统计。移动端触控、键盘和焦点顺序可用。

运行适当的 TypeScript、构建与现有回归检查，例如 `npm run typecheck`、`npm run build`、`npm test` 和相关 Playwright 用例。不需要执行 CDK 部署、bootstrap 或云端 smoke 来验收本次 UI。已有测试文字/定位因合理设计修改需同步更新，但不能把功能断言删掉；真实视频用例如依赖环境变量，应说明实际运行与跳过情况，不宣称已全部通过。

截图优先使用确定性本地 fixture 和真实本地展示产物，避免为了截图触发昂贵推理。交付桌面整体、标准全场/左右半场、未标定真实素材、已标定测试数据、移动端截图。清楚标注每张截图的数据状态，不能用测试雷达截图暗示当前视频已经完成真实标定。

完成时报告：修改了哪些 UI、关键实现和数据处理方式、实际通过的检查、截图位置，以及仍需球场标定数据才能启用的能力。最终页面应让人首先看到比赛、空间和解释，且每个显示出来的数据都能说明来源。
